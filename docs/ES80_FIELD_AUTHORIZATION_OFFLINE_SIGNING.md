# ES80 Field Authorization — Offline Signing Boundary (V14)

## Purpose

Nembra's package verifier can now cryptographically bind a software field authorization to two exact externally produced subjects:

- `NembraCaptureExternalBuildRecord.json` — the schema-v3 build/runtime identity record;
- `NembraCaptureFieldBuildEvidenceRecord.json` — the canonical field-build evidence record whose `signedInstallableSHA256` identifies the exact retained IPA.

`PassiveBluetoothCaptureFieldAuthorizationVerifier` uses authorization envelope schema **2** and authorization payload schema **2**. The payload decision vocabulary contains the literal string `GO`, but a signed envelope is **not physical Experiment One GO** by itself.

`scripts/ci/es80_field_authorization_envelope.py` creates that envelope on an offline/release-authority machine without placing the private key in the repository or app.

## Critical trust boundary

The authorization private key and the executable that receives it are external release-authority material.

The private key must never be:

- committed to Nembra;
- copied into the app bundle;
- written to an artifact uploaded by normal CI;
- printed in logs;
- generated by the app;
- selected by an app preference, Info.plist key, imported unsigned JSON, or UI control.

The signer refuses a private-key path that resolves inside the Nembra repository, requires a regular non-symlink owner-only key file, and on POSIX platforms requires the source key to be owned by the signing user. It also refuses to publish the signed authorization envelope inside the repository, reducing the chance that a build-specific signed `GO` payload is accidentally committed.

OpenSSL is also an explicit authority input. Production signing must provide `--openssl /absolute/path/to/openssl` or `NEMBRA_OPENSSL=/absolute/path/to/openssl`; the signer never discovers it from ambient `PATH`. The canonical executable must be a regular executable outside the repository, owned by root or the release-authority user, and neither it nor its canonical custody path may be group/world-writable. The executable identity is checked across each invocation.

The signer does **not** generate the production private key. Key creation, custody, backup, rotation, operator access, approved OpenSSL selection, and independent approval belong to the external release-authority process.

## One semantic parser

The offline signer intentionally does **not** decode or reinterpret either evidence record.

It reads each subject as exact immutable bytes, computes SHA-256, and signs only those exact digests. The Nembra package remains the semantic authority that closed-world parses the schema-v3 external build record and canonical field-build evidence record, checks their relationship, and checks the running executable + raw Info.plist identity.

This prevents the release tool from becoming a second evidence schema/parser whose rules can drift away from the app verifier.

## Envelope contract

The exact authorization payload contains:

```text
schemaVersion = 2
decision = GO
externalBuildRecordSHA256 = SHA-256(exact external-record bytes)
fieldBuildEvidenceRecordSHA256 = SHA-256(exact field-evidence bytes)
```

The external authority signs the **exact payload bytes** using P-256 ECDSA with SHA-256. The output signature is DER encoded, matching CryptoKit's `P256.Signing.ECDSASignature(derRepresentation:)` verifier path.

The envelope contains exactly:

```text
schemaVersion = 2
externalBuildRecordBase64
fieldBuildEvidenceRecordBase64
authorizationPayloadBase64
signatureDERBase64
```

The base64 fields preserve the exact signed subject/payload bytes. The package verifier rejects legacy schema v1, malformed or duplicate semantic fields, digest substitution, invalid signatures, mismatched evidence/build records, and running executable/Info.plist mismatch.

## Offline invocation

Use only after the exact signed IPA and its canonical evidence have been produced and independently reviewed. The private key and output envelope paths must be outside the repository. Select the reviewed OpenSSL executable explicitly; do not rely on shell `PATH` precedence.

```sh
python3 scripts/ci/es80_field_authorization_envelope.py \
  --openssl /usr/bin/openssl \
  --external-record /external/review/NembraCaptureExternalBuildRecord.json \
  --field-evidence /external/review/NembraCaptureFieldBuildEvidenceRecord.json \
  --private-key-pem /external/authority/nembra-field-authority-private.pem \
  --output-envelope /external/review/NembraCaptureFieldAuthorizationEnvelope.json
```

Equivalent release-authority automation may set `NEMBRA_OPENSSL=/absolute/reviewed/openssl` instead of passing `--openssl`.

The tool:

- requires an explicitly selected OpenSSL executable for production signing;
- canonicalizes that executable, rejects repository-controlled or group/world-writable executable/custody paths, and checks its identity across invocations;
- requires a P-256 / `prime256v1` private key;
- requires the key to be owner-only and, where POSIX ownership is available, owned by the release-authority user;
- opens the source key once with no-follow semantics and gives OpenSSL only the inherited descriptor path while creating an owner-only attempt-local snapshot;
- never reads the private-key bytes into Python;
- derives only the public uncompressed X9.63 point for review/pinning output;
- signs with OpenSSL ECDSA/SHA-256 using only the stable attempt-local key snapshot;
- immediately verifies its own signature using the derived public key;
- publishes the envelope with no-replace file creation;
- refuses input evidence files that are symlinks or change while being read;
- refuses repository-contained private-key or envelope-output paths.

Its stdout summary exposes only non-secret review facts: exact subject/payload/envelope SHA-256 values and the public X9.63 key/base64 + digest. It never prints the private key or key contents.

## Public-key pinning is a separate reviewed change

The signer reports `authorityPublicKeyX963Base64` and `authorityPublicKeyX963SHA256` so an independent reviewer can compare the external authority's public key with the package source change that will eventually configure:

```text
PassiveBluetoothCaptureFieldAuthorizationTrustAnchor.publicKeyX963Representation
```

Do **not** auto-edit or auto-pin the key from this script. The production trust root is deliberately `nil` today. Pinning the reviewed public key must be a separate exact-source decision on the final field lineage after key custody is established.

## Development self-test

```sh
python3 scripts/ci/es80_field_authorization_envelope.py --self-test
```

The no-argument development self-test intentionally uses the fixed system path `/usr/bin/openssl`, not ambient `PATH`. It may be overridden with `--openssl` or `NEMBRA_OPENSSL` when validating another explicitly reviewed executable.

The self-test generates an **ephemeral temporary** P-256 fixture key outside the repository, forces owner-only permissions, signs synthetic opaque subjects, verifies the signature, checks exact-byte/base64 preservation, checks the schema-v2 payload, checks no-replace output, rejects permissive key permissions, proves the one-descriptor signing snapshot remains stable after source-path replacement, and verifies repository-contained authority paths fail closed. Temporary key material is destroyed with its temporary directory.

Self-test success is development evidence only. It does not create or accept a production authority.

## What a cryptographically valid envelope still does not prove

Even if an independently held candidate key produces a signature that verifies, physical Experiment One remains blocked until all applicable V14 gates are deliberately closed, including:

1. the final composed Capture SHA has terminal exact-head app/package/UI acceptance;
2. the exact real signed/installable iPhone IPA is retained and independently accepted;
3. signing/provisioning evidence proves the intended field install conditions without leaking the device UDID;
4. the authority keypair is independently controlled and its reviewed public key is pinned in package source;
5. the signed envelope refers to those exact accepted evidence bytes;
6. the installed running app matches the accepted executable + raw Info.plist identity;
7. the package field execution gate deliberately consumes non-forgeable verified authorization rather than caller/UI state;
8. the definitive runbook records GO for that exact accepted build and procedure.

Until then:

**PHYSICAL EXPERIMENT ONE / FIRST REAL ES80 CAPTURE REMAINS NO-GO / DO NOT RUN.**
