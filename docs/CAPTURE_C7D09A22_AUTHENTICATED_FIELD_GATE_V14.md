# Capture C7D09A22 — authenticated stationary field gate (V14)

**Status:** software integration checkpoint; **PHYSICAL NO-GO until the private Tuya SDK/security component is installed, the exact app credentials are injected, the standalone target builds on the intended iPhone, and the in-app gates are satisfied.**

This procedure is the next smallest experiment after physical capture `C7D09A22-96DA-4E46-9BEF-E36F670ADB0E`. It replaces the old 17-step ride calibration for now.

## Why this exists

The first physical capture established:

- CoreBluetooth peripheral `6815A5F5-4D1E-E004-BAE8-6DF924123907`;
- Tuya service `FD50`;
- app-to-device characteristic `00000001-0000-1001-8001-00805F9B07D0`;
- device-to-app notify characteristic `00000002-0000-1001-8001-00805F9B07D0`;
- Tuya manufacturer company identifier `0x07D0`;
- successful CCCD notification enablement;
- zero application payload callbacks;
- repeatable peripheral rejection at about `29.93 s` across 15 observed drops.

That evidence says the next question is authentication/session establishment, not another movement experiment.

## Hard safety boundary

This build must not:

- synthesize, guess, fuzz, replay, or brute-force raw FD50 authentication frames;
- derive a BLE session key from `local_key`;
- issue a DP control command;
- unbind, reset, factory-reset, pair-reset, activate, or re-authorize the scooter;
- change speed limit, lock, light, ride mode, cruise, motor, brake, calibration, or firmware state;
- export account passwords, AppKey, AppSecret, access/refresh tokens, `local_key`, session/auth keys, or other credentials.

The custom Tuya QR bridge remains metadata/ownership discovery only. It is never BLE authentication authority.

## Private SDK provisioning

The official SmartLife SDK integration is intentionally split into public Git state and private local material.

1. In the Tuya Developer Platform, use the SmartLife App SDK application whose iOS Bundle ID exactly matches:

   `com.jonathangana131.nembra.capturelearn`

2. Download the app-specific iOS security component generated by Tuya. Keep its `Build/` directory and `ThingSmartCryption.podspec` private.

3. At the repository root, create this ignored local directory:

   `.nembra-tuya-sdk/`

   Place the generated `Build/` directory and `ThingSmartCryption.podspec` directly inside it.

4. Run `pod install` at repository root. The checked-in `Podfile` refuses to proceed when the private security podspec is missing.

5. Open `NembraCapture.xcworkspace` after CocoaPods generation, not the bare project for this SDK-backed build.

6. For the **Nembra Capture** scheme, inject these values privately in the Xcode Run environment:

   - `NEMBRA_TUYA_APP_KEY`
   - `NEMBRA_TUYA_APP_SECRET`

   Never add the literal values to Git, a runbook, screenshot, issue, PR, JSON artifact, or chat transcript.

7. Build/install the exact candidate on the intended iPhone. Simulator execution may validate UI/fallback behavior but never authorizes the physical experiment.

## In-app procedure — stationary only

Keep the scooter stationary for this entire gate.

1. Launch Nembra Capture.
2. Confirm **SDK compiled = Yes**, **Private app config = Injected**, and **SDK initialized = Yes**.
3. If the official SDK account is not already authorized, sign into the user's own Tuya account through the in-app official SDK login surface. Nembra clears its password field immediately after requesting login and does not put the password into exported diagnostics.
4. Separately use the metadata QR link to identify the already-bound scooter and select it. This step does not authenticate BLE.
5. Enter **Secure stationary test** only after the official SDK account gate says Authorized.
6. With the scooter OFF, start the OFF baseline and save it after a short observation.
7. Turn the scooter ON, keep it still, and scan again.
8. Select only a strong deterministic target. The prior physical CoreBluetooth UUID is strongest existing evidence; `FD50 + 0x07D0` is also accepted target-correlation evidence. Name/RSSI alone never authorize the target.
9. Tap **Start official read-only session**.
10. Do not touch scooter controls while the session is being evaluated.

## Mechanical acceptance contract

The app may display **authenticated capture gate passed** only when the same current attempt has all of these:

1. `ThingSmartBLEManager` reports the Tuya UUID is currently locally connected;
2. that current official local-BLE state has survived at least **45 monotonic seconds**;
3. `ThingSmartDeviceDelegate` delivered at least one non-empty application DP update;
4. the supplemental CoreBluetooth observer captured at least one non-empty post-auth notification on `00000002-0000-1001-8001-00805F9B07D0` while the official local session was current.

The official connect success callback alone is **not** accepted connection authority.

If official local-BLE currentness is lost, its duration anchor is discarded and the attempt fails closed.

## Diagnostic outcomes

### PASS

Export the sanitized JSON and stop. This closes the authentication/continuity/raw-payload gate. It does **not** establish any DP meaning yet.

The next experiment after a pass is a small stationary mapping sequence chosen from the newly observed payload structure, not the old full ride.

### Official application payloads arrive, but raw FD50 bytes do not

Export diagnostics and stop. This is meaningful evidence that the official authenticated session works, but it does not satisfy Nembra's raw-byte capture requirement. Do not compensate by repeating the ride or by guessing frames.

### Official BLE remains connected but no application payload arrives

Export diagnostics after the stationary observation and stop. Do not infer DP semantics from cloud metadata alone.

### Official local BLE disconnects / repeats the old ~30-second pattern

Export diagnostics and stop. Do not automatically retry forever and do not proceed to movement.

## Export contract

The authenticated diagnostic JSON may contain:

- selected CoreBluetooth peripheral UUID;
- Tuya device UUID/product ID identifiers needed for provenance;
- candidate evidence;
- official local-BLE currentness state;
- authenticated monotonic duration;
- application callback count;
- application DP callback JSON when serializable;
- raw FD50 notification bytes in hex and Base64;
- monotonic/wall-clock event receipt metadata;
- explicit `secretsRedacted: true` and `dpCommandsSent: false` markers.

It must not contain passwords, AppKey, AppSecret, cloud tokens, `local_key`, session/auth keys, or generated Tuya security-component bytes.

## Truth boundary after PASS

A pass establishes only:

- the official Tuya SDK can establish/maintain a local session to the already-bound selected device;
- application callbacks exist in that session;
- Nembra captured raw post-auth FD50 notification bytes during the current official session.

A pass does **not** by itself establish battery, voltage, current, watts, speed, brake, throttle, light, mode, odometer, charging, command acknowledgement, rated maximum, or any other DP semantic.
