# Production Visual Capture Coverage Gaps — 2026-08-06

Worker: `chat-w6r8f`
Lane: `production-visual-audit`

## Purpose

This document audits **what Nembra's current Xcode 27 Simulator gate actually captures**, so future visual work does not mistake a green build or a handful of screenshots for production visual acceptance.

It is intentionally read-only guidance. The active UI-test, ride-lifecycle, Dashboard battery/readout, and performance workers own their implementation files; this lane does not modify their tests or product code.

## Current capture pipeline

At current `main`, `scripts/ci/xcode27_simulator_capture.sh` does all of the following on the self-hosted Xcode 27 runner:

1. resolves an available iOS 27 runtime;
2. prefers an iPhone 12 Simulator device type;
3. runs the full Xcode test bundle and exports kept XCTest attachments;
4. installs the built app;
5. normalizes the Simulator status bar;
6. launches named simulation scenarios and captures direct screenshots after a two-second settle;
7. preserves logs, the result bundle, attachments, and scripted screenshots as Actions artifacts.

This is a strong foundation because the screenshots are generated by the **real app** on the real project/test target rather than by static mockups.

## P0 evidence gap — floating tab/content clearance is not asserted

The accepted Ride Details screenshot visibly showed the floating Home/Rides tab chrome overlapping the lower route/coverage area. Current source explains the root asymmetry: Home alone receives a fixed bottom safe-area reserve, while the Rides NavigationStack does not.

The current Ride UI test:

1. opens the completed ride;
2. swipes up only if the route map is initially absent;
3. asserts the map exists;
4. captures a screenshot.

It does **not** scroll to the end and assert that the final route/evidence row is fully clear of floating tab chrome.

### Required future acceptance assertion

For every tab-root/detail surface with scrollable content, a production visual test should:

- navigate through the real tab/root stack;
- scroll to the content end;
- resolve the last meaningful tappable/readable element;
- assert that its visible frame does not intersect the floating tab bar's visible frame;
- capture that bottom-of-content state;
- repeat on iPhone 12 with the actual iOS 27 tab behavior.

Do not encode `72 pt` as a universal test truth. The current Home value is an implementation detail, and native tab-bar geometry/behavior can vary with system presentation.

## P1 gap — signature battery/range states

The final product requires a battery instrument that toggles `% ↔ estimated remaining range`, while keeping the battery icon/fill semantically tied to charge state and never inventing range.

Current scripted captures prove:

- ordinary connected battery percentage;
- low-battery warning;
- retained battery while reconnecting.

They do **not** yet prove:

- the percentage → estimated-range interaction;
- estimated range unavailable / learning states;
- numeric learned range once an accepted estimator reaches the app;
- interruption/replanning of a battery integer transition;
- consistency between Home, Dashboard, and live ride;
- VoiceOver values in both modes;
- Reduce Motion behavior for the toggle;
- charging presentation once charging truth exists.

PR #57 currently owns Dashboard primary battery-readout UI integration. This audit deliberately does not duplicate it. After that lane lands, the visual gate should expand around the accepted interaction contract rather than inventing parallel UI here.

## P1 gap — Dashboard composition states

Current attachments prove a useful functional subset:

- moving landscape;
- every confirmed stopped mode personality;
- stopped control touch-target checks.

Still missing from production visual acceptance:

- low-battery Dashboard while moving;
- reconnecting Dashboard during a legitimately continuous ride;
- disconnected/unsupported Dashboard behavior where applicable;
- battery percentage vs estimated-range modes;
- long ride duration/trip values and width stress;
- unusually long vehicle identity strings;
- very large accessibility text where the cockpit supports it;
- Reduce Motion result state;
- navigation active;
- rerouting/recalculating;
- navigation ended and cockpit restored;
- map + telemetry under runtime load;
- right-to-left/localization stress if later supported.

The future visual test should preserve the existing invariant that high-frequency speed presentation remains isolated and never turns interpolated frames into telemetry evidence.

## P1 gap — Home state depth

The direct scripted matrix is broad, but each state is captured only shortly after launch and primarily at the top/initial viewport.

Production coverage still needs:

- bottom-of-scroll Home with floating tab chrome visible;
- connected Home after real confirmed control changes;
- primary battery readout in both modes;
- active ride with enough duration/trip data to stress layout;
- recovered ride with truthful retained/live distinctions;
- long localized vehicle/detail values;
- Dynamic Type / accessibility sizes;
- Reduce Motion interaction result;
- empty/unavailable secondary data without layout collapse;
- dark-mode low battery and key error states where contrast differs materially.

The goal is not to double every screenshot mechanically. Add variants where the alternate state can expose a real hierarchy, contrast, geometry, or truth bug.

## P1 gap — Rides and Ride Details

Current screenshots use a one-item history fixture and one route-bearing ride. They do not expose the performance and product-design problems likely to appear with real history.

Production coverage should include:

### History
- empty history;
- one ride;
- enough rides to require substantial scrolling;
- mixed complete/recovered/partial-evidence rides;
- rides with route and no-route states;
- unavailable/failed persistence state;
- pull-to-refresh result;
- bottom-of-list tab clearance;
- Dynamic Type / accessibility sizing.

### Details
- full route coverage;
- partial route with known gaps;
- coordinates recorded but insufficient continuous points to draw a path;
- no route geometry;
- route-store failure/unavailable;
- odometer-only evidence;
- GPS-only evidence;
- unresolved/multiple evidence sources;
- recovered ride;
- bottom-of-detail tab clearance;
- map region/annotation behavior with realistic route spans.

Truth semantics remain unchanged: missing route data must never produce a decorative fake route, and independent distance evidence must not be silently promoted to a final total.

## P1 gap — transition evidence

A screenshot captured after a two-second settle cannot validate motion quality.

The final visual pass needs runtime/interacted evidence for:

- rolling speed digits and carry/borrow direction;
- battery integer progression;
- battery `% ↔ range` toggle;
- confirmed mode change;
- stopped ↔ moving Dashboard control changes;
- reconnection state changes;
- automatic ride activation/recovery;
- navigation insertion/removal and cockpit rearrangement;
- map camera changes;
- interrupted animations;
- Reduce Motion alternatives.

For animation acceptance, use a combination of deterministic interaction tests, runtime observation, frame/performance profiling where appropriate, and endpoint screenshots. Do not create synthetic telemetry packets solely to make animation look smooth.

## P1 gap — performance evidence packaged with visual evidence

The current Xcode gate proves build/test success and preserves screenshots/logs, but the Production Visual + Performance Overhaul eventually needs repeatable performance checkpoints for the same critical states.

At coherent release checkpoints, pair screenshots with evidence such as:

- launch/transition responsiveness;
- Dashboard CPU/main-thread behavior during realistic telemetry updates;
- Dashboard + navigation/map behavior together;
- long-history scrolling;
- memory growth during long simulated ride sessions;
- route rendering with realistic point counts;
- no whole-screen invalidation caused by speed/battery animation.

Do not run heavyweight profiling on every small PR. Add it at coherent visual/performance acceptance milestones.

## Recommended capture architecture — without taking implementation ownership

When an integration/visual owner is ready to expand the harness, prefer these principles:

1. **Keep shell screenshots cheap.** Scripted launch-state screenshots are excellent for broad connection/error regressions.
2. **Use XCUI for stateful visuals.** Navigation, scrolling, tab clearance, battery toggle, mode changes, and ride-detail states need real interaction.
3. **Name attachments by user-visible state, not phase number.** Artifacts should remain understandable after architecture evolves.
4. **Assert before capture.** A screenshot should accompany a semantic/geometry assertion when the bug is machine-checkable.
5. **Keep exact-head identity.** Artifact/run metadata must make the tested commit unambiguous.
6. **Do not screenshot fake product truth.** Simulator fixtures are allowed QA inputs, but the artifact/readme must never present them as physical ES80 measurements.
7. **Avoid a screenshot explosion.** Prioritize states with meaningfully different geometry, interaction, warning hierarchy, or evidence coverage.

## Suggested first regression to automate after shell ownership is clear

The highest-value visual regression is the currently demonstrated P0 defect:

> `Ride Details can scroll its final meaningful content completely clear of the floating iOS 27 tab bar on iPhone 12.`

That test is narrow, user-visible, source-backed, and independent of unfinished battery/range/navigation domains. It should be implemented by the eventual root/shell owner because `AppRootView.swift` is a v5 high-contention surface.

## Acceptance boundary

This document does not claim current screenshots are production-visual acceptance, does not modify test coverage, and does not create physical-device evidence.

Its durable conclusion is that Nembra already has enough real Simulator infrastructure to support a serious visual regression program, but the current capture matrix is optimized for **functional systems validation**. The final Production Visual + Performance phase must deliberately expand it around shell clearance, signature battery/range interaction, integrated cockpit/navigation states, realistic ride history, accessibility/motion, and performance before visual completion can be claimed.
